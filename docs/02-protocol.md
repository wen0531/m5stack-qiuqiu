# 通信协议（BLE + WebSocket + HTTP）

> 本文以仓库代码为唯一依据，描述手表侧固件、手机 App、电脑桥三方之间的线路协议与消息语义。
> 代码与注释／旧描述不一致时以代码为准，冲突处集中在附录 A 列出。
> 所有速率、包长均按代码常量推算；涉及"实测"的结论一律标注，未标注者为推算值。

## 1. 总览

### 1.1 链路分层

```
┌─ 手表（ESP32-S3） ───────┐           ┌─ 手机 App ───────────────┐           ┌─ 电脑桥 ─────────────────┐           ┌─ 云端／本机 ─────────────┐
│ 麦克风 44.1 kHz          │           │ GATT 客户端              │           │ aiohttp /ws              │           │ 流式 ASR                 │
│ IMA-ADPCM 16 kHz         │───BLE────▶│ 上行 164 B／包           │───WSS────▶│ ADPCM 解码               │───HTTP───▶│ 后台 Agent               │
│ 喇叭 44.1 kHz            │◀───BLE────│ 下行 244 B／包           │◀───WSS────│ Opus 编码                │◀──HTTP────│ TTS 合成                 │
│ A／B 两个按键            │           │ 断线自动重连             │           │ ASR／TTS 编排            │           │ 对话历史                 │
└──────────────────────────┘           └──────────────────────────┘           └──────────────────────────┘           └──────────────────────────┘
```

三个物理段各自独立成帧：BLE 段是"4 字节头 + 载荷"，WS 段只传载荷（App 负责补头／剥头），
桥与云端之间是 WAV 与 JSON。

```

 │ 长按 A ≥ 500 ms           │                           │                           │

 │                           ├─────────cmd:start────────▶│                           │

 │                           │                           ├──────────调用识别────────▶│
```

按键语义：A 键长按 ≥ 500 ms 为按住说话，且仅在球球 App 前台时武装（`voice_set_ptt_enabled`）；
播放中按 A 表示打断，该次按键被吞掉，直到松手才重新武装（`s_ptt_suppressed`）。

### 1.3 时延量级（估算，未逐一实测）

| 环节 | 量级 | 依据 |
|---|---|---|
| 按下到首包发出 | 约 20 ms | 一帧采集周期 |
| 上行 BLE 传输 | 实时 | 净荷 8 kB/s，50 包／秒 |

## 2. BLE 层

### 2.1 广播与连接参数

| 项 | 值 | 说明 |
|---|---|---|
| 广播名 | `StopWatch-BLE` | 同时作为 GAP 设备名 |
| 广播内容 | 128 位服务 UUID，complete list | 手机可按服务过滤，App 实际按名字过滤 |
| 广播类型 | 可连接无向、通用可发现 | 不需要配对与绑定，无加密 |
| 广播间隔 | 前 30 s 为 100 ms，之后 1 s | 掉线后重连快，稳态省电 |
| 音频态连接间隔 | 30–50 ms（24–40 单位），延迟 0 | 上行 50 包／秒与下行 16.7 包／秒都能容纳 |
| 空闲态连接间隔 | 100–150 ms（80–120 单位），从机延迟 4 | 只在空闲时启用 |
| 监督超时 | 5 s（500 单位） | 两种模式相同 |
| 首选 MTU | 400（两端都设） | 手机在服务发现后 `requestMtu(400)` |

进入音频态：开始说话、开始播放；退出音频态：停止说话（未在播放）、播完、被打断。

### 2.2 服务与特征

服务 UUID 前缀固定为 `4f5a00xx-1e3b-4d8a-9c7e-5a1b2c3d4e5f`。

| 名称 | UUID | 属性 | 方向 | 长度 | 说明 |
|---|---|---|---|---|---|
| 语音服务 | `4f5a0001-…4e5f` | PRIMARY | — | — | 广播中携带 |
| 控制 | `4f5a0002-…4e5f` | WRITE、WRITE_NO_RSP | 手机 → 手表 | 缓冲 8 B；协议用 1–2 B | 命令码，见 2.3 |
| 音频 | `4f5a0003-…4e5f` | NOTIFY、WRITE、WRITE_NO_RSP | 双向 | 通知 164 B；写入受 MTU 限（本地缓冲 512 B） | 上行音频／事件／调试，下行音频 |
| 状态 | `4f5a0004-…4e5f` | READ、NOTIFY | 手表 → 手机 | 读 8 B；通知 2 B | 状态快照与事件 |
| CCCD | `00002902-0000-1000-8000-00805f9b34fb` | 标准 | 手机 → 手表 | — | 音频与状态各一个 |

要点：

1. 控制特征只写不可读，`ctrl_access` 对读操作直接返回错误。
2. 音频特征同时承担四个方向／用途：上行音频（codec 1）、事件（codec 0x7E）、调试（codec 0x7F）、下行音频（写入）。
3. "就绪"的判定是"已连接且音频通知已订阅"（`ble_svc_ready`）；只订阅状态特征不算就绪，此时不会采集也不会发事件。
4. 手机订阅顺序为音频、状态；两个 CCCD 都写 `ENABLE_NOTIFICATION_VALUE`。

### 2.3 控制命令码

命令只有单槽缓冲（`s_pending_cmd`／`s_pending_val`），新命令在未被消费前写入会覆盖旧的；
`requeue` 仅在槽空时生效。命令只在 `voice_task` 非说话状态被消费。

| 码 | 名称 | 载荷 | 消费位置 | 行为 | 状态 |
|---|---|---|---|---|---|
| `0x00` | TALK_OFF | 1 B | `ctrl_access` | `s_remote_talk=false`，停止远端说话 | 已接线（App 不发） |
| `0x01` | TALK_ON | 1 B | `ctrl_access` | `s_remote_talk=true`，等效于远端按住说话 | 已接线（调试用） |
| `0x02` | PING | 1 B | `ctrl_access` | 仅打日志，不产生其他状态；会话活跃计数仍 +1 | 已接线（调试用） |
| `0x10` | 背光 | `[0x10, 亮度 0..255]` | 入队 | 无消费者：球球只认 `0x30`，其余回抛给语音任务，语音任务不处理 `0x10` | 保留（当前无效果） |
| `0x20` | 表情 | `[0x20, 表情 0..14]` | 入队 | 同上，无消费者 | 保留（当前无效果） |
| `0x30` | 帧缓冲转储 | 1 B | `AppQiuqiu::onRunning` | 把当前球球帧 RLE 编码后走 `0x7F` 通道 | 已接线（需球球前台） |
| `0x31` | 单音 1 kHz | 1 B | `voice_task` | 0.4 s，经 `HAL::audioPlay` | 已接线（调试） |
| `0x32` | 单音 1.5 kHz | 1 B | `voice_task` | 0.4 s，经 `audioWriteStream` | 已接线（调试） |
| `0x33` | 开机音效 | 1 B | `voice_task` | `playBootSfx()` | 已接线（调试） |
| `0x34` | 长音 | 1 B | `voice_task` | 440 Hz、0.8 s | 已接线（调试） |
| `0x35` | —— | —— | 无 | BLE 层未受理，写入被忽略 | 未实现（编号空档） |
| `0x36` | 声称"切 16 kHz 播放" | 1 B | `voice_task` | 空分支，不改采样率 | 已受理／空实现 |
| `0x37` | 声称"切回 44.1 kHz" | 1 B | `voice_task` | 空分支 | 已受理／空实现 |
| `0x40` | 电池 CSV 导出 | 1 B | `voice_task` → `batt_log_dump` | 走 `0x7F` 通道流式输出 CSV | 已接线 |
| `0x50` | 后台配色 | `[0x50, 0..2]` | `voice_task` → `set_agent_color` | 0 白、1 蓝、2 红 | 已接线 |

补充：

1. 写入方式：App 对 `0x50` 用"无响应写"，对 `0x40` 用"有响应写"；其余调试命令未在 App 中实现。
2. `0x50` 是幂等的，App 会连发 4 次（0／350／800／1400 ms）以冗余对抗丢包，固件不做确认。
3. 配色索引由桥下发：`agents.json` 里每个后台的 `color` 字段随 `{"type":"agent","active":…}` 一起发给 App，App 不再认识具体后台名称；
   固件只认索引，不认名字。改名需同步桥与 App（见附录 A）。
4. 命令在播报期间可写但不会被消费，`0x40` 因此需要 App 侧等待通道空闲（见 6.5）。

### 2.4 状态特征

**读（8 字节，手动读取快照）**

| 偏移 | 长度 | 含义 |
|---|---|---|
| 0 | 1 | 已连接 = 1，否则 0 |
| 1 | 1 | 音频通知已订阅 = 1 |
| 2 | 1 | 远端说话中 = 1（`s_remote_talk`） |
| 3–6 | 4 | 已成功发送的音频包数，小端 |
| 7 | 1 | 发送错误计数，超过 255 截断为 255 |

**通知（2 字节：事件码 + 0）**

| 事件 | 含义 | 固件附带动作 |
|---|---|---|
| `0x10` | 开始说话 | 连接切到音频态 |
| `0x11` | 说话结束 | 未在播放则回到空闲态 |
| `0x12` | 开始播放 | 连接切到音频态；保存当前音量 |
| `0x13` | 播放结束 | 回到空闲态，恢复保存的音量 |

注意：通知要求状态特征已订阅（`s_status_subscribed`），未订阅时 `ble_svc_status_notify` 直接返回。
正常播完与被打断都会发 `0x13`；打断时额外在事件通道镜像一次。

### 2.5 事件通道 `0x7E`（音频特征上的可靠事件）

部分手机收不到状态特征的通知，因此关键事件在音频通知里再发一份。

```
偏移 0..1  seq（小端，实现恒为 0，接收端不校验）
偏移 2     0x7E
偏移 3     事件码
```

| 事件 | 触发 | 手机动作 |
|---|---|---|
| `0x13` | 播报被 A 键打断 | 发 `{"cmd":"stop_play"}` 让桥停止发帧 |
| `0x20` | 球球前台按下 B 键 | 发 `{"cmd":"agent_next"}` 让桥切下一个后台 |

约束与差异：

1. 该通道依附音频通知，未订阅则整条通道不可用（`s_subscribed` 为假时直接返回）。
2. `0x20` 只走事件通道，状态通道从不发 `0x20`；但 App 在两条通道上都认 `0x20`，属于历史兼容。
3. 正常播完只发状态 `0x13`，不发事件 `0x13`；只有打断才双发。
4. 事件包只有 4 字节，序号字段固定为 0，与音频包序号互不影响。

### 2.6 调试通道 `0x7F`（CSV／二进制透传）

```
偏移 0..1  seq（小端，仅在单次调用内从 0 递增；接收端不使用）
偏移 2     0x7F
偏移 3     0
偏移 4..   任意字节，单包长度 = MTU − 3 − 4
```

| 项 | 值 |
|---|---|
| 单包载荷 | `MTU − 7`（MTU 400 时为 393 B，见下方限制） |
| 分包单位 | 一次 `ble_svc_debug_send` 调用内部循环分包；序号是调用内局部量，多次调用之间不连续 |
| 接收端处理 | App 仅在"正在导出电池"时把 `data[4:]` 按 UTF-8 追加，否则整包丢弃 |
| 发送失败 | 计入 `s_tx_errors`，不重传 |

使用者与内容：

| 触发 | 内容 |
|---|---|
| 控制 `0x40` | 首行 `uptime_s,vbat_mv,pct`，每行 `秒,毫伏,百分比`，尾行 `batt,done`；无样本时只有 `batt,no samples` |
| 控制 `0x30` | 球球帧缓冲的 RLE：每段 4 字节 `[run_lo, run_hi, px_lo, px_hi]`，像素为 RGB565，单次上限 32 kB |

限制：发送端局部缓冲只有 260 字节（`uint8_t pkt[260]`），而分包长度按 MTU 计算。
MTU 400 时单包载荷 393 字节会超出该缓冲，因此调用方应自行把单次调用限制在 ≤ 256 字节。
电池 CSV 路径每次调用 ≤ 220 字节（行缓冲 220 B），符合约束；帧缓冲路径单次可达 32 kB，
在大 MTU 下的行为见附录 B 的未验证项。

### 2.7 MTU 与包长

| 包 | 总长 | 需要的 MTU | 备注 |
|---|---|---|---|
| 上行音频通知 | 164 | ≥ 167 | 不足则丢包并累加 `tx_errors` |
| 下行 ADPCM | 164 | ≥ 167 | 8 kB/s |
| 下行 Opus 32 kbps | 244 | ≥ 247 | 240 B 载荷；MTU 247 恰好用满 |
| 下行 Opus 24 kbps | 184 | ≥ 187 | 180 B 载荷（默认档） |
| 下行 PCM16 | 4 + 2N | ≥ 7 + 2N | 受写入缓冲 512 B 限制，单包最多 254 样本 |
| 事件 `0x7E` | 4 | ≥ 7 | |
| 调试 `0x7F` | 4 + n | ≥ n + 7 | 受 2.6 的 256 B 约束 |

协商路径：固件在初始化与建链时都设首选 MTU 400；手机在服务发现后请求 400。
若协商失败退回默认 23（单包 20 字节），所有音频包都会被固件丢弃，现象是"能连上但无声"，
且状态特征里包数不增长、错误数持续增长——这是排查无声的第一个检查点。

## 3. 音频包格式

统一约定：所有包的第 2 字节是 codec id，第 3 字节是标志位（当前恒为 0，接收端忽略）。

| codec id | 含义 | 上行 | 下行 |
|---|---|---|---|
| 0 | PCM16 小端原始样本 | 不用 | 仅链路自测，桥不产生 |
| 1 | IMA-ADPCM 4 bit | 默认上行 | 备选下行 |
| 2 | Opus | 代码保留（默认关闭） | 默认下行 |
| `0x7E` | 事件（非音频） | 事件通道 | 不用 |
| `0x7F` | 调试（非音频） | 调试通道 | 不用 |

### 3.1 上行 ADPCM（默认路径）

```
偏移 0..1   seq（小端，每次开讲从 0 开始）
偏移 2      codec = 1
偏移 3      flags = 0
偏移 4..163 160 字节 IMA-ADPCM（低半字节在前，每字节 2 个样本）
```

| 参数 | 值 |
|---|---|
| 总长 | 164 字节 |
| 采样率 | 16 kHz 单声道 |
| 帧长 | 20 ms = 320 样本 |
| 数据量 | 160 B／帧，50 帧／秒，净荷 64 kbps，含头 65.6 kbps |
| 编码状态 | 每次开讲 `adpcm_reset`，帧间连续预测，丢包会造成短时失真 |

采样链：ES8311 以 44.1 kHz 单声道采集 882 样本（20 ms），线性插值到 320 样本 16 kHz，
再编码为 160 字节。插值按 `step = (882 − 1) / (320 − 1)` 做一维线性重采样。

代码里另有一条上行 Opus 路径（16 kHz、60 ms、16 kbps、复杂度 5），由编译期宏
`UPLINK_OPUS` 控制，当前为 0，即关闭。启用后包长改为 `4 + 编码长度`，序号与 codec id 同步改 2，
但手机上行为未验证。

### 3.2 下行 Opus（默认路径）

```
偏移 0..1   seq（小端，手机自增并按 65536 取模；手表不校验）
偏移 2      codec = 2
偏移 3      flags = 0
偏移 4..    Opus 自定界包，一帧一包
```

| 参数 | 值 | 依据 |
|---|---|---|
| 采样率／声道 | 16 kHz 单声道 | `opus.py` |
| 帧长 | 60 ms = 960 样本 | 同上 |
| 码率 | 默认 24 kbps，可调 32 kbps | `OPUS_BITRATE` |
| 32 kbps 包长 | 240 B 载荷 → 244 B 总长 | 32000 × 0.06 ÷ 8 |
| 24 kbps 包长 | 180 B 载荷 → 184 B 总长 | 24000 × 0.06 ÷ 8 |
| 编码模式 | VOIP、复杂度 5、CBR（VBR=0）、不做前向纠错 | 同上 |
| 包率 | 16.7 包／秒 | 1 ÷ 0.06 |
| 桥侧编码缓冲 | 512 B | `opus.py` |

CBR 是刻意选择：包长恒定，MTU 与 BLE 写入都能按固定上限设计。

### 3.3 下行 ADPCM 与 PCM16

下行 ADPCM（`codec=1`，`DOWNLINK_CODEC=adpcm` 时启用）：

| 参数 | 值 |
|---|---|
| 帧长 | 20 ms = 320 样本 |
| 载荷 | 160 B → 总长 164 B |
| 包率 | 50 包／秒 |
| 桥侧节拍 | 每包后休眠 20 ms（按实时速率发送） |

下行 PCM16（`codec=0`）：载荷为小端 int16 原始样本，仅用于验证"手机→手表写通路"，
桥不下发；手表侧单包样本数上限 254（写入缓冲 512 B），解码缓冲为 2400 样本。

### 3.4 手表侧播放节奏

| 项 | 值 | 说明 |
|---|---|---|
| 环形缓冲 | 32000 样本（16 kHz、2 s） | 满则丢弃新样本 |
| 起播预缓冲 | 3200 样本（200 ms） | 不足不开始 |
| 写入节拍 | 每 20 ms 取 320 样本 → 插值 882 样本 @44.1 kHz → 写 I2S | 固定节奏，不随抖动调整 |
| 起播淡入 | 20 ms（882 样本） | 避免爆音 |
| 软限幅 | 拐点 29500，向上平滑压缩 | 防止削顶 |
| 中途欠载 | 补静音继续，不重置、不停播 | |
| 播完判定 | 连续欠载 2 s | 触发状态 `0x13`、恢复音量、连接回空闲态 |
| 打断 | 清空环形缓冲 + 置中断标志 | 写入器补约 400 ms 静音排空 DMA 后停写 |

下行队列：BLE 写入先进 64 槽 × 512 字节的环形队列（约 3.8 s 余量），由下行任务每 2 ms 取一包处理；
队列满时静默丢弃。包长小于 6 字节或 codec id 不是 0／1／2 的包被丢弃。
Opus 解码器在包间隔超过 500 ms 时复位，用于区分前后两段播报。

桥侧发送节奏：先以背靠背方式推 `HEAD_START_MS`（默认 300 ms）的帧，让手表攒够预缓冲，
之后按媒体时钟对齐发送，避免累积漂移。

## 4. WebSocket 协议（手机 ↔ 桥）

### 4.1 端点与帧类型

| 项 | 值 |
|---|---|
| 加密端点 | `wss://<桥地址>:8443/ws`，自签证书，App 对该链路采用信任全部证书 |
| 明文端点 | `ws://<桥地址>:8444/ws`，仅供本机或内网调试 |
| 文本帧 | UTF-8 JSON，一类带 `cmd`（手机发起），一类带 `type`（桥发起） |
| 二进制帧 | 单向下行音频（桥 → 手机）；上行音频由手机以二进制帧发往桥 |
| 连接数 | 桥只保留最后一个 App 连接，新连接直接覆盖旧连接 |

### 4.2 `cmd`（手机 → 桥）

| cmd | 附带字段 | 桥的动作 | 回包 |
|---|---|---|---|
| `start` | — | 复位会话，进入录音态 | `{"type":"recording","on":true}` |
| `stop` | — | 落盘 WAV → ASR → 后台 → TTS → 下行播放 | `saved`、`asr`、`thinking`、`reply`、`speaking`、`done` 依次 |
| `agent_status` | — | 无 | `{"type":"agent","active":…,"source":"sync"}` |
| `agent_next` | — | 按固定顺序切下一个后台 | `{"type":"agent","active":…,"source":"bkey"}` |
| `agent` | `name` | 切换后台并写入配置 | `{"type":"agent","active":name}` 或 `{"type":"agent","error":…}` |
| `stop_play` | — | 置停止标志，后续帧不再发送 | 无 |
| `battery` | — | 桥 → 手机，触发电池日志拉取 | 手机回 `battery_csv` |
| `play` | `file` | 调试用：读 WAV 并以 ADPCM 下行播放 | `{"type":"played","file":…}` |

表中 `battery` 是唯一反向的 cmd：由桥发往手机，触发电池日志拉取；其余 cmd 均由手机发起。
`agent_next` 的顺序在桥里写死为三个后台名，与 `agents.json` 的键必须一致；
名字不匹配时切换会抛异常并断开本次会话（见附录 A）。

### 4.3 `type`（桥 → 手机）

| type | 字段 | 触发 | App 行为 |
|---|---|---|---|
| `recording` | `on` | 收到 `start` | 仅记录日志 |
| `saved` | `file`、`seconds` | `stop` 落盘后 | 日志 |
| `asr` | `text` | ASR 完成 | 日志；空串表示识别失败 |
| `thinking` | — | 调后台之前（回声模式不发） | 无处理，仅透传日志 |
| `reply` | `text` | 后台返回 | 日志 |
| `speaking` | — | 下发首帧之前 | 日志"手表播放中" |
| `done` | — | 末包后 1.3 s | 日志"播放完毕" |
| `codec` | `id` | 每段音频开始前 | 设置下行 codec（1 ADPCM／2 Opus） |
| `agent` | `active`、`source`、`error` | 切换或同步 | 非 `bkey` 来源时写 `0x50` 配色 |
| `level` | `samples` | 录音中约每秒 1 条 | 无处理，诊断用 |
| `battery_csv` | `data` | 电池导出完成（手机 → 桥） | — |
| `played` | `file` | 调试播放完成 | 无处理 |

顺序约束：`codec` 必须先于该段音频的二进制帧；`speaking` 先于首帧；`done` 晚于末帧。
App 只在收到 `codec` 后改变包头的 codec id，因此桥每段都会重发一次。

### 4.4 二进制帧

| 方向 | 内容 | 长度 | 说明 |
|---|---|---|---|
| 手机 → 桥 | 上行 ADPCM 载荷 | 160 B | 已剥离 4 字节 BLE 包头，64 kbps／50 包每秒 |
| 桥 → 手机 | 下行编码包 | 240／180／160 B | 原始编码帧，未加包头 |

手机侧在转发下行包时补 4 字节头：`seq`（自增，取模 65536）、`codec`（当前值）、`flags=0`。
桥侧不关心手机补的序号，手表也不校验。

### 4.5 一次会话的消息序列

```
 手机                                            桥
 │ {"cmd":"start"}                               │
 │◀────────{"type":"recording","on":true}────────│
 │ [二进制 160 B] × N（边说边发）                │
 │ {"cmd":"stop"}                                │
 │◀────{"type":"saved","file":…,"seconds":…}─────│
 │◀───────────{"type":"asr","text":…}────────────│
 │◀──────{"type":"thinking"}（非回声模式）───────│
 │◀──────────{"type":"reply","text":…}───────────│
 │◀───────────{"type":"codec","id":2}────────────│
 │◀─────────────{"type":"speaking"}──────────────│
 │◀──────────────[二进制 240 B] × M──────────────│
 │◀───────────────{"type":"done"}────────────────│
 │                                               │
```

若用户说"换个话题"之类的复位语，桥在 `asr` 之后先清空对话历史并播放一句确认，再继续；
若识别到后台别名，桥先切后台、回 `agent` 并播放一句确认，剩余文本作为本轮问题。

## 5. HTTP 接口（桥）

| 方法 | 路径 | 用途 | 返回 |
|---|---|---|---|
| GET | `/` | 网页调试页（Web Bluetooth，仅 TLS 实例提供） | HTML |
| GET | `/ws` | WebSocket 升级 | — |
| GET | `/battery` | 让手机拉取手表电池日志并返回 CSV | 200 `{ok,file,csv}`；503 无手机连接；504 超时 |
| GET | `/agent` | 查询当前后台 | `{active, available}` |
| POST | `/agent` | 切换后台，参数取自查询串 `name` 或 JSON `{name}` | 200 `{ok,active}`；400 未知后台 |

细节：

1. `/battery` 内部最多等 32 s（固件按每行 15 ms 输出，1440 行约 22 s），成功后把完整 CSV 存盘，
   响应里只回前 2000 字符。
2. 明文端点的应用只挂载 `/ws`、`/battery`、`/agent`，没有 `/` 网页。
3. 两个端点共享同一个会话对象，因此同一时刻只能有一路录音；新的 `start` 会复位共享会话。

## 6. App 内部机制

### 6.1 首帧即开会话

状态事件 `0x10` 可能丢失，因此 App 在收到第一条 `codec=1` 的音频通知时，若本地 `talking` 为假，
就补发一次 `{"cmd":"start"}`，并把该帧正常转发。这样即使 `0x10` 丢了，桥也不会漏掉整段录音。
事件 `0x10` 与首帧同时到达时只会开会话一次（`talking` 置位后不重复发送）。

### 6.2 900 ms 静音自动停

`0x11` 同样可能丢失，因此每次开会话都启动一个 250 ms 轮询的看门狗：
距上一帧超过 900 ms 即判定说完，发 `{"cmd":"stop"}` 并停止计时。
看门狗只在 `talking` 为真时运行，收到 `0x11` 后自然结束。

### 6.3 MAC 自动重连

| 机制 | 行为 |
|---|---|
| 记住地址 | 首次扫描到设备后把 MAC 写入偏好设置 |
| 后台连接 | 启动时优先用 `connectGatt(autoConnect=true)` 直连已知 MAC，可跨手表重启 |
| 扫描兜底 | 后台连接返回失败则扫描；按名字 `StopWatch-BLE` 过滤 |
| 无过滤扫描 | 连续 2 次未命中后取消名字过滤（部分机型广播名匹配会失效） |
| 扫描看门狗 | 独立线程每 3 s 检查，14 s 无结果就重启扫描 |
| 断线重连 | 断链后 2 s 重扫；服务启动与保活任务每 30 s 兜底检查 |
| WS 重连 | 失败或关闭后 3 s 重连，并按候选地址轮换 |

候选地址顺序：用户手填地址（唯一，不轮换）→ 局域网地址（仅 Wi-Fi 时）→ 动态域名 → 回环地址（ADB 反向隧道）。

### 6.4 codec 切换

下行 codec 由 `{"type":"codec","id":n}` 设置，默认 1（ADPCM）。每段播报开始前桥都会重发，
App 收到后仅更新一个字段，随后所有二进制帧按该值填包头第 2 字节。
网页调试页写死 `codec=1`，因此桥若配置为 Opus，网页端会解错（见附录 A）。

### 6.5 电池导出

1. 桥发 `{"cmd":"battery"}`。
2. App 先检查通道是否忙（1500 ms 内有上行音频，或仍在播放），忙则每 2 s 重试，最多 40 次。
3. 空闲后向控制特征写 `0x40`（有响应写），同时清空收集缓冲并开始 26 s 计时。
4. 期间收到的 `0x7F` 包按 UTF-8 追加；计时结束后发 `{"type":"battery_csv","data":…}`。
5. 无论是否收到 `batt,done` 尾行都会在 26 s 后发送，超时意味着 CSV 可能被截断。
6. 桥的 `/battery` 再把这份文本落盘并回给调用方。

## 7. 错误与降级

### 7.1 事件通知的四级兜底

| 级别 | 手段 | 覆盖的问题 |
|---|---|---|
| 1 | 状态特征通知 `0x10`／`0x11` | 正常路径 |
| 2 | 事件通道 `0x7E` | 打断（`0x13`）与 B 键（`0x20`）需要可靠送达；该通道不承载 `0x10`／`0x11` |
| 3 | 首帧音频隐含 `start` | 状态通知 `0x10` 丢失 |
| 4 | 900 ms 静音看门狗 | 状态通知 `0x11` 丢失，会话不会结束 |

对应地，固件在播完与打断上做了区分：播完只发状态事件，打断双发，因为打断必须尽快让桥停发，
否则手表会继续收到已被丢弃的帧，浪费带宽。

### 7.2 打断链路

```
A 键按下（播放中）
  ├─ voice_task：清空下行环 → 置中断标志 → 恢复音量 → 连接回空闲态
  │    ├─ 状态特征 0x13
  │    └─ 事件通道 0x13
  │         └─ App：playingUntil 归零 → {"cmd":"stop_play"}
  │              └─ 桥：STOP_PLAY=true
  │                   ├─ 正在发送的循环立即 return（不发 done）
  │                   └─ 后续帧不再产生
  ├─ 写入器：补约 400 ms 静音排空 DMA，之后停写
  ├─ 下行任务：中断期间丢弃迟到的帧，防止环形缓冲被重新填满
  └─ 下一次开讲：清除中断标志并再次清空环形缓冲，恢复正常播放
```

被打断时桥不会补发 `done`，所以 App 的"播放完毕"提示只由手表的状态事件驱动；
若 `0x13` 也丢失，App 侧的播放态最多靠 8 s 的本地超时自然过期。

### 7.3 后台与语音链路失败

| 失败点 | 现象 | 降级行为 |
|---|---|---|
| ASR 返回空 | `asr` 文本为空 | 不调后台、不回复，手表静默回到空闲；无提示音 |
| 后台抛异常或超时 | 无回复文本 | 回固定话术"抱歉，我现在没法回答。" |
| TTS 失败 | 只有 `reply`，没有音频 | 手表不进入播放态，App 日志仍显示回复文本 |
| 桥未连上 | App 的发送为空操作 | 手表正常录音，但音频无人接收 |
| BLE 未就绪（音频未订阅） | 状态显示未连接 | 不采集、不发事件；界面显示"困倦"态 |
| BLE 初始化失败 | 无广播 | 固件继续启动，球球与原厂应用可用，只是没有语音 |
| MTU 协商失败 | 能连上但无声 | 上行全部丢弃，状态特征里包数不涨、错误数增长 |

### 7.4 安全边界

当前协议没有配对、绑定、加密与鉴权：任何人连上即可读状态、订音频、写控制。
明文 WS 端点同样没有鉴权，只应绑在回环或可信内网。外网访问依赖传输层（反向代理 TLS）
与网络层（VPN／隧道）收敛，协议本身不提供访问控制。

# StopWatch 语音手表 踩坑与修复记录

> 记录 2026-10-21 ~ 10-23 期间遇到的所有真实故障、根因与修复方式。
> 目的：以后再遇到同类现象，能 5 分钟内定位，不用重新试错。

## 一、固件 / 硬件类

### 1. A 键松手崩溃（Guru Meditation: StoreProhibited）
- **现象**：按住 A 说话，松手瞬间设备重启
- **根因**：面板 DMA 缓冲 `buf[0]`/`buf[1]` 为 NULL 时仍执行 memcpy
- **修复**：`Panel_AMOLED.cpp` 加空指针保护
- **教训**：双缓冲切换时，两个缓冲都要判空

### 2. 按住 A 一直"滴滴滴"
- **现象**：录音时喇叭连续响
- **根因**：音频 DMA 队列（12×512 帧 ≈ 140ms）排不空，硬件循环播最后一段
- **修复**：播放结束后补 **4×100ms 静音**排空 DMA
- **教训**：任何"停止播放"都要考虑 DMA 余量，不能立刻停写

### 3. 屏幕莫名熄灭
- **现象**：松手后 3s / 13s 黑屏
- **根因**：`think_until` 只设了 8s；后改 30s
- **修复**：等待回复期间持续 `markActivity()`

### 4. 屏幕休眠导致 SPI 死锁（设备挂死）
- **根因**：熄屏/唤醒的面板 I/O 分布在多个任务里并发访问 SPI
- **修复**：所有面板电源 I/O 收敛到 `screenTick()`（主循环单一上下文）

### 5. Opus 下行"嗡嗡响"
- **现象**：换成 Opus 解码后持续嗡嗡/破音
- **根因**：`esp_audio_dec_out_frame_t.len` 是**缓冲区容量**，被当成已解码长度用 → 每帧多塞 1440 个未初始化 PSRAM 样本（噪声比语音高 15dB）
- **修复**：改用 `frame.decoded_size / 2`；解码缓冲改 `heap_caps_calloc`；每次播放前 `esp_opus_dec_reset()`
- **教训**：ESP-ADF 系列结构体里 `len` 常是"容量"，输出长度另有字段

### 6. 起播阈值写错导致**完全没声音**
- **根因**：起播阈值设 4800 样本，但每次最多只取 3200（`BLOCK_IN`）→ 永远达不到
- **修复**：阈值改 3000（< BLOCK_IN）
- **教训**：所有"等待 N 个样本再播"的阈值必须 ≤ 单次可取的块大小

### 7. 播放"一顿一顿"、词被切断
- **根因**：播放器按固定 200ms 块输出，而 Opus 帧是 60ms，200/60 除不尽 → 每块差 20–60ms 就断一下
- **修复**：改成"攒够 20ms 就播"，固定 20ms 节奏 + 200ms 起播预缓冲
- **教训**：播放块大小必须与编码帧长对齐（或做成时间无关的自适应）

### 8. 破音（越加增益越破）
- **根因**：不是数字削波，是**喇叭机械失真**——设置里音量 95 + 固件再 ×1.6 增益
- **修复**：增益回 1.0，音量跟随系统设置（100% 实测不破）
- **教训**：小喇叭在接近满幅时物理失真，软件加增益只会更糟

### 9. 命令"发出去没反应"（0x40 电池 / 0x50 换色）
- **根因**：`app_qiuqiu.cpp` 和 `voice_task.cpp` **各有一个命令消费循环**，Qiuqiu 先取走但只处理 0x30，其余直接丢弃
- **修复**：新增 `ble_svc_requeue_command()`，Qiuqiu 不认识的命令退回队列
- **教训**：共享队列有多个消费者时，必须"不认识就归还"

### 10. 无响应写（write-without-response）被静默丢弃
- **现象**：颜色指令偶发失灵、电池读不到
- **根因**：NimBLE 对 no-response 写会静默丢包
- **修复**：改成 `WRITE_TYPE_DEFAULT`（带响应）；颜色改为冗余发送 4 次

### 11. 开机后串口无输出 / 设备"死机"
- **根因**：`esptool --after no_reset` 刷完，芯片停在**下载模式**（`boot:0x3 (DOWNLOAD)`），根本没启动
- **修复**：刷完必须物理拔插 USB 让它正常启动
- **教训**：**判活前先确认没有停在下载模式**；light sleep 也会让 USB 控制台断流，不能用串口判断死活

### 12. light sleep 导致真·挂死
- **现象**：开 light sleep 后黑屏、不广播、连刷写都不响应
- **根因**：QSPI 屏驱动（M5GFX 直写寄存器 + DMA）不持 `ESP_PM_APB_FREQ_MAX` 锁；light sleep 关 USB-JTAG；唤醒后板级外设无恢复路径
- **结论**：**这块板放弃 light sleep**。官方 M5StopWatch-UserDemo 也没开（`CONFIG_PM_ENABLE is not set`），只做面板休眠
- **可用替代**：DFS 调频 + BLE modem sleep（已实测稳定）

## 二、蓝牙 / App 类

### 13. 手表重启后 App 永远搜不到
- **根因**：Android 复用被连接过的 `ScanCallback` 会**静默不回调**；且 App 依赖扫描找设备
- **修复**：① 每次扫描用全新回调；② **记住 MAC 用 `autoConnect=true` 后台连接**，绕开扫描器
- **效果**：App 重启后 0.5 秒自动连上（不用再扫描）

### 14. 状态通知（0x10/0x11）在部分手机收不到
- **根因**：该机型上 status 特征的 notify 不可靠
- **修复**：改用**音频特征**上的事件通道（codec 0x7E）；App 改为"收到第一帧音频即开始会话"，不再依赖状态通知

### 15. 桥在发音频时阻塞自己的消息接收
- **现象**：手表按 A 打断，桥 33 秒后才响应
- **根因**：`await send_downlink()` 在 WS 接收协程里同步执行，收不到新消息
- **修复**：播放放到 `asyncio.create_task()` 后台任务；收到 `stop_play` 立刻置标志中断

## 三、后台 / 数据类

### 16. DSH 后台偶发 404
- **现象**：手表回复 "HTTP_404: DeepSeek Messages request failed"
- **根因**：dsh CLI 内部调用偶发失败，且**错误文本被当成正常回答**返回
- **修复**：`_looks_like_error()` 做**大小写不敏感**检测，命中则自动降级到下一个后台；过滤 `mem0-local MCP server started` 噪声

### 17. 电池数据导不全
- **根因**：固件整环 1440 行 × 15ms ≈ 21.6s，但 App 只收 6s、PC 脚本只收 5s
- **修复**：App 26s、脚本 26s、桥等待 32s；导出前等待语音通道空闲

## 四、通用教训

1. **判活手段要可靠**：串口会因 light sleep 断流；用 BLE 广播/连接、电池读取、屏幕状态判断
2. **刷机后必须物理拔插**（`no_reset` 会停在下载模式）
3. **多个消费者共享队列 → 不认识就归还**
4. **BLE 小包写优先用带响应**，无响应会静默丢
5. **小喇叭不要靠软件增益提音量**
6. **块大小与帧长对齐**，别假设整除
7. **官方固件是最好的基线**：M5 官方也没做 light sleep，说明这条路在他们眼里不划算
